
Wisualyst Intelligence Platform
POC Developer Brief
1. Objective
Build the first working Proof of Concept of the Wisualyst Intelligence Platform, a modular data, analytics and AI platform that connects directly to a company’s operational data, standardizes that data into a common intelligence layer, runs selected analytical and optimization modules, and makes the outputs available both inside Wisualyst and to external reporting platforms.
The platform should not behave like a collection of dashboards.
The architecture should support the following progression:
Source Data → Data Integration → Data Model → Intelligence Modules → Recommendations → Reporting Layer
The POC scope consists of four modules:
Module 1: AI Inventory Optimization
Module 3: AI Demand Forecasting
Module 4: Intelligent Procurement Optimizer
Module 8: Retail Assortment & Space Optimizer
These modules come from the larger Supply Chain Intelligence Platform concept. The underlying product vision is to move beyond descriptive dashboards toward:
What happened → Why did it happen → What will happen → What should we do next


2. What the Platform Is
Wisualyst should sit between a company’s operational systems and its decision making tools.
It should be thought of as an intelligence layer rather than another ERP or another BI application.
A company may already have:

10. Critical Architectural Principle
The AI modules must not directly depend on SFTP, Zoho or a specific database schema.
This is important.
Instead:
SFTP
      \
Database → Ingestion Layer → Canonical Data Model → Intelligence Modules
      /
Zoho
Every connector converts source data into the platform’s standardized internal data model.
The modules then consume standardized data.
Therefore, adding SAP, Odoo, NetSuite or another connector later should not require rebuilding the Inventory, Demand or Procurement models.

21. Important MCP Implementation Detail
Power BI, Qlik Sense and Google Sheets should be treated as target integrations, rather than assuming each product itself exposes the exact MCP interface Wisualyst needs.
The architecture should therefore create:
Wisualyst MCP Layer
plus
Application Adapters
For example:
                    Wisualyst Intelligence API
                              ↓
                         MCP Layer
                              ↓
          ┌───────────────────┼───────────────────┐
          ↓                   ↓                   ↓
   Power BI Adapter     Qlik Adapter       Sheets Adapter
          ↓                   ↓                   ↓
       Power BI           Qlik Sense        Google Sheets
This allows each adapter to use the authentication and API method required by the corresponding application while exposing a consistent MCP tool interface from the Wisualyst side.

37. Product Philosophy for Development
The engineering team should continuously preserve five principles.
Principle 1: Connect Once
Customer data should be connected once and reused across multiple modules.
Principle 2: Map Once
The canonical data layer prevents every module from rebuilding source mappings.
Principle 3: Intelligence Before Visualization
Forecasts, optimization and recommendations belong inside Wisualyst.
Reporting tools visualize the outputs.
Principle 4: Modular Architecture
Every future Wisualyst module should be able to plug into the same platform.
Principle 5: Explain Every Recommendation
The platform should not only output:
“Order 1,400 units.”
It should explain:
Why
Based on which data
Expected impact
Confidence
Alternative action


38. The Simplest Way to Explain the Product to the Development Team
Wisualyst is the intelligence layer between enterprise data and enterprise reporting.
Companies connect data to Wisualyst through:
SFTP + Direct Database + Zoho
Wisualyst standardizes that data and runs:
Inventory AI + Demand AI + Procurement AI + Assortment AI
Those modules produce:
KPIs + Forecasts + Risks + Recommendations + Optimized Decisions
The results appear inside:
Wisualyst Control Tower + Module Workspaces
and are exposed through:
MCP + APIs
to:
Power BI + Qlik Sense + Google Sheets
for report creation and business consumption.
Or, in one line:
Connect → Map → Validate → Understand → Predict → Optimize → Recommend → Report
That should be the architectural backbone of the POC.
